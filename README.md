# 시니어 일상훈련 인지케어 웹앱

고령자(특히 경도인지장애·정상 고령층)를 위한 **일상생활 기반 인지훈련** 웰니스 웹앱입니다.
추상적인 "뇌게임"이 아니라 장보기·요리 같은 **실제 일상 과제를 게임화**해, 훈련 후에는
"오늘 실제로 해보기" 미션으로 앱 밖 행동까지 이어지도록 설계했습니다.

> **이 앱은 웰니스 서비스이며 의료기기가 아닙니다.**
> 이 앱은 건강한 생활습관을 돕는 웰니스 서비스이며, 의료적 진단·치료를 대체하지 않습니다.
> "치매 예방/치료/진단" 같은 의료 효과를 주장하지 않고, "두뇌 건강 습관" · "일상 능력 지키기" 같은
> 표현만 사용합니다. 이 원칙은 카피뿐 아니라 기능 설계(예: 적응형 난이도·기능 프로파일 점수)에도
> 그대로 반영되어 있습니다 — 자세한 내용은 [기능 프로파일 & 적응형 난이도](#기능-프로파일--적응형-난이도) 참고.

전체 제품 스펙과 마일스톤 계획은 [`SPEC.md`](./SPEC.md)에 있습니다.

## 실행하기

```bash
npm install
npm run dev       # 개발 서버 (기본 http://localhost:5173)
```

빌드 / 미리보기:

```bash
npm run build      # dist/ 에 프로덕션 빌드 (manifest.webmanifest + sw.js 포함)
npm run preview    # 빌드 결과를 로컬에서 미리보기 (http://localhost:4173)
```

**서비스 워커는 `npm run dev`에서 동작하지 않습니다.** 개발 중 캐시 때문에 코드 수정이
화면에 반영되지 않는 문제를 막으려고 일부러 꺼 두었습니다. 홈화면 추가·오프라인 동작을
확인하려면 `npm run build && npm run preview` 쪽을 쓰세요.

별도의 백엔드·계정·로그인이 없습니다. 모든 데이터는 브라우저의 `localStorage`에만 저장되며,
서버로 전송되는 정보는 전혀 없습니다. 처음 실행하면 지난 2주치 데모용 더미 기록이 자동으로
채워져(9장 참고), 훈련을 하지 않아도 가족 화면이 곧바로 의미 있게 보입니다.

## 기술 스택

| 영역 | 선택 |
|---|---|
| 프레임워크 | React 18 + Vite |
| 언어 | **JavaScript만 사용** (TypeScript 미사용) |
| 스타일 | Tailwind CSS v3.4 (고령자 접근성 토큰을 `tailwind.config.js`에 커스텀 정의) |
| 라우팅 | react-router-dom |
| 상태관리 | Zustand |
| 차트 | Recharts (기능 프로파일 시각화) |
| 저장소 | 브라우저 `localStorage`만 (서버 없음) |
| 음성 안내 | Web Speech API (`SpeechSynthesis`), 기본값 꺼짐 |
| PWA | vite-plugin-pwa (manifest + 서비스 워커, 오프라인 동작, 홈화면 추가) |

의도적으로 하지 않은 것: 백엔드/계정/로그인, 실제 지도 API, 결제, 드래그 앤 드롭, 다크모드,
3D 그래픽. 이유는 [`SPEC.md` 12장 비목표](./SPEC.md#12-비목표-하지-말-것) 참고.

**규칙 두 가지가 코드 전체에 일관되게 적용되어 있습니다.**

- `localStorage`는 `src/lib/storage.js` 한 곳에서만 접근합니다. 다른 파일은 전부 `useAppStore`를
  통해서만 데이터를 읽고 씁니다.
- 클릭 가능한 요소는 항상 `<button>`입니다(`<div onClick>` 없음). 순서를 정하는 과제는 모두
  드래그 없이 "탭으로 하나씩 고르기" 방식입니다.

## 화면 구성

하단 큰 탭 3개(**홈 · 훈련 · 가족**)만 있는 단순한 구조입니다. 설정은 홈에서 진입합니다.

1. **온보딩** — 이름·나이대(선택)·글자크게·음성안내를 4단계로 입력. 로그인 없음.
2. **홈** — 오늘의 추천 훈련, 연속 사용일(스트릭), 오늘의 실생활 미션, 기능 프로파일 요약, 설정 진입.
3. **훈련** — 게임 카드 목록 (장보기·요리 순서 맞추기, 이후 마일스톤에서 길찾기·복약 추가 예정).
4. **훈련 플레이** — 게임별 화면. 흐름은 "안내 → 잠깐 보여주고 가림 → 탭으로 재현 → (상위 레벨) 응용 문제".
5. **결과** — 잘한 점을 먼저 보여주고, "오늘 실제로 해보기" 실행 브리지 미션을 제안.
6. **가족** — 같은 기기의 `localStorage`를 읽어 **이번 주 활동 요약**을 보여주는 보호자용 화면.
   점수가 아니라 활동량(영역별 횟수·누적 횟수)만 보여줍니다 — 이유는
   [설계 판단](#설계-판단) 참고.
7. **설정** — 글자 크게, 음성 안내, 데이터 초기화, 웰니스 고지.

## 게임(훈련)

각 게임은 순수 로직(`*Logic.js`)과 화면(`.jsx`)을 분리해 두어, 게임 규칙만 따로 콘솔이나
스크립트에서 검증할 수 있습니다.

### 장보기 미션 (`games/Shopping.jsx`, `shoppingLogic.js`)
- **영역:** 작업기억(항상) + 계산(레벨 4 이상)
- 장바구니 목록을 잠깐 보여준 뒤 가리고, 가상 진열대에서 탭으로 담습니다. 담은 것은 다시 눌러
  뺄 수 있고 벌점이 없습니다.
- 목록은 **하드코딩하지 않고** `recipes.js`의 요리 재료에서 만듭니다 — 그래야 "오늘은 미역국을
  끓입니다" 같은 실생활 맥락이 생기고, 코스 모드(마일스톤 9)를 붙일 때도 수정이 필요 없습니다.
- 레벨 4~5에서는 계산대 단계가 추가되어 "○○원을 내면 잔돈은?" 문제를 2~3문항 풉니다(레벨 4는
  1,000원권 단위, 레벨 5는 10,000원권 단위라 더 어렵습니다). 문항이 여럿이라 정확도가 0%/100%
  둘로만 나오지 않습니다.
- 난이도 레버: 목록 길이 · 노출 시간 · 방해 품목 수 · 계산 문항 수/단위.

### 요리 순서 맞추기 (`games/Cooking.jsx`, `cookingLogic.js`)
- **영역:** 순서화(항상) + 실행기능(레벨 4 이상, 재료 계량 문제)
- 조리 순서를 잠깐 보여준 뒤 가리고, 뒤섞인 단계 카드를 **드래그 없이** "몇 번째로 할 일을
  고를지" 탭으로 하나씩 선택해 재현합니다. 잘못 골랐으면 그 항목을 눌러 그 순번부터 다시
  고를 수 있습니다.
- 레벨 4 이상에서는 "물 두 컵의 절반은?" 같은 재료 계량 문제가 2문항 추가됩니다.
- 한국적 소재(밥·미역국·김치찌개·잡채·불고기 등)로 구성된 `recipes.js` 더미 데이터를 장보기와
  공유합니다.
- 난이도 레버: 단계 수 · 노출 시간 · 방해 단계 수 · 계량 문항 포함 여부.

두 게임 모두 끝나면 결과 화면에서 "오늘 실제로 해보기" 실행 브리지 미션(예: "오늘 저녁에
미역국을 직접 만들어 가족과 나눠 먹기")을 제안하고, 담으면 홈의 오늘 미션 목록에 쌓입니다.

## 기능 프로파일 & 적응형 난이도

마일스톤 5에서 구현한, 이 앱의 "학습형" 핵심 로직입니다. **의료적 판정처럼 보이지 않게 하는
것이 기능 요구사항 그 자체**라는 점이 특징입니다.

### 적응형 난이도 — `lib/adaptive.js`
- 게임마다 레벨 1~5가 있고(`levels{}`), 성적에 따라 **조용히** 오르내립니다. 화면 어디에도
  "난이도를 낮췄습니다" 같은 문구나 레벨 숫자 자체를 노출하지 않습니다.
- **비대칭 규칙:** 올리는 건 신중하게(같은 영역에서 **연속 3세션** 정확도 85% 이상), 내리는 건
  상대적으로 빠르게(**연속 2세션** 정확도 50% 미만). 너무 어려운 과제가 주는 좌절감이 너무 쉬운
  과제가 주는 지루함보다 이탈로 이어지기 쉽다고 보고, 실패 경험이 쌓이는 쪽을 먼저 막습니다.
- 레벨이 바뀌면 그 뒤 세션부터 새 레벨 값으로 기록되므로, 스트릭 계산이 자동으로 초기화됩니다
  (별도 카운터를 저장하지 않습니다) — 레벨업 직후 곧바로 두 단계를 건너뛰지 않습니다.
- 한 게임에 영역이 둘이어도(예: 장보기의 작업기억+계산) 판의 난이도는 하나이므로, 그 게임이
  항상 만들어 내는 "대표 영역"(장보기=작업기억, 요리=순서화) 성적만 보고 조정합니다.

### 기능 프로파일 — `lib/profile.js`
- 영역별로 0~100점을 매겨 홈·가족 화면 차트의 축 하나를 이룹니다.
- **최근 세션에 더 큰 가중**을 주되, 달력상 며칠이 지났는지는 보지 않습니다 — 훈련을 며칠
  쉬었다가 돌아와도 그 자체로 점수가 깎이지 않습니다. 꾸준함은 스트릭·세션 수로 별도 표시합니다.
- 정확도만 보지 않고 **레벨을 반영**합니다(레벨 1의 100%가 레벨 5의 80%보다 높게 나오지
  않도록, 레벨마다 도달 가능한 점수 천장을 다르게 둡니다).
- **최소 3세션 미만인 영역은 점수를 만들지 않고** "아직 기록이 적어요"로만 표시합니다 — 1세션
  만에 100점이 뜨는 일이 없습니다.
- "정상/주의/저하" 같은 등급이나 신호등 색, 또래 비교는 쓰지 않습니다. 낮은 축은 "아직 덜
  해본 활동"으로만 표현합니다.

### 차트 — 홈과 가족이 서로 다른 것을 봅니다

| | 홈 (`ProfileChart.jsx`) | 가족 (`ActivityMixChart.jsx`, `CumulativeTrainingChart.jsx`) |
|---|---|---|
| 보는 사람 | 본인 | 보호자 |
| 축에 얹는 값 | 영역별 **0~100 점수** | 영역별 **이번 주 훈련 횟수** / **누적 횟수** |
| 이유 | 자기 흐름을 스스로 확인하는 자리 | 점수는 "몇 점짜리 상태인가"로 읽히기 쉬운 자리 |

세 차트가 공통으로 지키는 규칙:

- **실제 세션이 있는 영역만** 축으로 그립니다(영역 목록을 코드에 고정하지 않음) — 아직 없는
  게임의 영역이 0점 축으로 표시돼 "못한다"는 오해를 주지 않기 위해서입니다.
- 축 3개 이하는 막대 차트, 4개 이상은 레이더 차트로 자동 전환합니다.
- 값은 차트뿐 아니라 **항상 보이는 숫자 목록으로도 병기**합니다(색만으로 정보를 전달하지 않기
  위해, 그리고 hover에 의존하지 않기 위해). 그래서 차트 그림 자체는 `aria-hidden`으로 두고
  포커스 대상에서 뺐습니다 — Recharts가 기본으로 붙이는 이름 없는 `tabindex=0` 칸에 포커스가
  멈추면 키보드 사용자에게 아무것도 알려주지 못하기 때문입니다.
- 축마다 색을 달리하지 않습니다. 많고 적음에 좋고 나쁨이 붙지 않게 하기 위해서입니다.
- "글자 크게"를 켜면 rem 기반 레이아웃은 저절로 커지지만 Recharts에 넘기는 폭·폰트 크기는
  숫자(px)라 자동으로 따라오지 않습니다. 이 폭 값을 계산하는 `scale`이 바뀔 때 차트를 강제로
  다시 그리게 해(`key={scale}`) 좁은 화면에서 잘리는 문제를 막습니다.
- 차트 애니메이션은 꺼 두었습니다(`isAnimationActive={false}`). 고령자용 화면에 필요 없기도
  하지만, 마일스톤 7 점검에서 **애니메이션이 첫 프레임에 멈춰 레이더가 반지름 0인 점으로만
  그려지던 버그**를 발견해 고친 것이기도 합니다.

## 설계 판단

이 앱에서 "왜 그렇게 했는가"가 코드보다 중요한 결정들입니다. 대부분 **고령자 대상**이라는
조건과 **웰니스 서비스(의료기기 아님)**라는 조건에서 나왔습니다.

### 1. 순서 배열에 드래그 앤 드롭을 쓰지 않았다

요리 순서 맞추기는 전형적으로 드래그로 만드는 과제입니다. 쓰지 않은 이유는 세 가지입니다.

- **손떨림.** 드래그는 "누른 채로 정확한 위치까지 이동해서 뗀다"는 세 동작을 끊김 없이
  이어가야 성공합니다. 본태성 진전이나 파킨슨 증상이 있으면 중간에 손가락이 떨어지거나
  목표를 지나쳐 실패합니다. 인지 과제를 풀지 못한 게 아니라 **손이 미끄러져서** 틀리는데,
  기록에는 똑같이 오답으로 남습니다. 측정하려는 것을 측정하지 못하게 됩니다.
- **마우스와 터치의 동작이 다르다.** 데스크톱의 HTML5 drag 이벤트와 모바일의 touch 이벤트는
  좌표계·취소 조건·스크롤 충돌이 서로 다릅니다. 태블릿에서는 세로 스크롤과 드래그가
  구분되지 않아 목록이 통째로 따라 움직이는 문제까지 생깁니다.
- **되돌리기가 어렵다.** 잘못 놓았을 때 "원래 자리로 되돌리는" 동작이 또 한 번의 드래그입니다.

대신 **탭으로 하나씩 고르기**로 만들었습니다. "몇 번째로 할 일"을 순서대로 한 번씩 누르면
되고, 잘못 골랐으면 그 항목을 눌러 **그 순번부터** 다시 고를 수 있습니다. 한 번의 탭은
떨림이 있어도 성공률이 높고, 마우스·터치·키보드 Tab+Enter가 전부 동일하게 동작합니다.
(`SPEC.md` 3.1 — 드래그 앤 드롭 사용 금지)

### 2. 난이도 레벨 숫자를 사용자에게 보여주지 않는다

레벨은 내부적으로 1~5까지 있고 성적에 따라 오르내리지만, 화면 어디에도 "레벨 3",
"난이도를 낮췄습니다" 같은 표시가 없습니다.

- **레벨 숫자는 곧 성적표가 된다.** "나는 레벨 2인데 지난달엔 3이었다"는 순간, 훈련이
  자기 상태를 확인하는 시험이 됩니다. 인지 기능이 걱정되어 이 앱을 여는 사람에게 그 확인은
  훈련을 이어가게 만드는 힘이 아니라 그만두게 만드는 힘으로 작용합니다.
- **난이도가 내려간 것은 실패가 아니다.** 컨디션이 나쁜 날, 잠을 못 잔 날에도 난이도는
  내려갑니다. 그걸 통보하면 하루의 컨디션이 능력 저하의 신호처럼 읽힙니다.
- 그래서 조정은 **조용히** 이루어지고, 화면에는 긍정 신호만 보여줍니다.

조정 규칙 자체도 비대칭입니다 — 올릴 때는 연속 3세션 85% 이상으로 신중하게, 내릴 때는
연속 2세션 50% 미만으로 비교적 빠르게. 너무 어려운 과제가 주는 좌절이 너무 쉬운 과제가 주는
지루함보다 이탈로 이어지기 쉽다고 보고, **실패 경험이 쌓이는 쪽을 먼저 막습니다.**

### 3. 프로파일 점수는 훈련을 쉬어도 내려가지 않는다

`lib/profile.js`는 최근 세션에 더 큰 가중을 주지만, 그 "최근"은 **달력 날짜가 아니라 순번**
입니다. 열 번째 최근 세션이 2주 전이든 두 달 전이든 가중치는 같습니다.

- **사실에 맞습니다.** 2주 쉬었다고 해서 그 사람의 작업기억이 실제로 나빠졌다는 근거는
  이 앱에 없습니다. 앱이 아는 것은 "그동안 새 기록이 없다"는 것뿐입니다. 없는 데이터를
  하락으로 바꿔 표시하면 그건 측정이 아니라 추측입니다.
- **그 추측이 하필 의료적으로 읽힙니다.** "쉬었더니 점수가 떨어졌다"는 화면은 사용자에게
  기능 저하의 증거처럼 보입니다. 웰니스 앱이 해서는 안 되는 판정입니다(`SPEC.md` 4장).
- **동기 부여 측면에서도 반대로 작동합니다.** 오랜만에 돌아온 사람에게 가장 먼저 보여줄
  것이 깎인 점수라면, 그 사람은 다시 앱을 열지 않습니다.

꾸준함은 점수를 깎는 방식이 아니라 **스트릭과 훈련 횟수라는 별도 지표**로 보여줍니다.
같은 이유로 최소 3세션 미만인 영역은 점수를 만들지 않고 "아직 기록이 적어요"로만 둡니다 —
표본 1개로 100점을 띄우는 것도, 그 100점이 나중에 떨어지는 것도 둘 다 사실이 아니기
때문입니다.

### 4. 가족 리포트는 절대 점수가 아니라 활동량으로 표현한다

마일스톤 6까지는 가족 화면도 홈과 같은 영역별 점수(52점·55점…)를 보여줬습니다.
마일스톤 7에서 **가족 화면에서만** 걷어냈습니다. 홈의 점수 표시는 그대로 둡니다.

- **보는 사람이 다르면 같은 숫자가 다르게 읽힙니다.** 본인에게 "작업기억 52점"은 자기
  흐름의 한 점입니다. 그러나 보호자에게는 **부모의 상태를 나타내는 지표**로 읽힙니다.
  52라는 숫자에는 기준선이 없는데도, 사람은 100점 만점을 가정하고 "절반밖에 안 된다"로
  읽습니다. 앱이 하지 않은 판정을 화면이 대신 해버리는 셈입니다.
- **비교가 시작됩니다.** 지난주와, 형제자매의 부모와, 인터넷에서 본 누군가와. 이 앱에는
  또래 규준도 임상 기준도 없으므로 그 비교는 전부 근거 없는 비교입니다.
- **오독의 결과가 무겁습니다.** 보호자가 리포트를 보고 걱정하거나 안심하는 것은 실제 의사
  결정(병원에 갈지 말지)으로 이어질 수 있습니다. 근거 없는 숫자가 그 결정에 끼어들면 안 됩니다.

그래서 가족 화면은 **"이번 주에 무엇을 얼마나 하셨는가"**만 보여줍니다. 영역별 축에는 점수
대신 **훈련 횟수**를 얹었습니다. 같은 레이더라도 짧은 축의 의미가 "이 영역을 못한다"에서
"이 영역을 덜 하셨다"로 바뀝니다.

주별 그래프도 같은 이유로 바꿨습니다. 원래는 주마다의 훈련 횟수를 그렸는데, 바쁜 주가 지나면
다음 막대가 짧아집니다. 라벨도 색도 중립으로 뒀지만 **짧아진 막대는 그 자체로 "줄었다"로
읽힙니다.** 그래서 **누적 횟수**로 바꿨습니다. 누적 그래프는 내려갈 수 없고, 쉰 주는 짧아지는
대신 평평해집니다. 이미 하신 것이 사라지지는 않으니 사실에도 더 맞습니다.

점수 계산 함수(`lib/profile.js`)는 지우지 않았습니다. 홈에서 계속 쓰기 때문입니다.
가족 화면에서 **호출하지 않을 뿐**입니다.

### 5. 웰니스 표현만 쓰고 의료 효과를 주장하지 않는다

앱 전체에서 "치매 예방/치료/진단/지연" 같은 표현을 쓰지 않고, "두뇌 건강 습관",
"일상 능력 지키기", "꾸준한 활동"만 씁니다.

- **사실이 아니기 때문입니다.** 인지훈련이 치매를 예방한다는 주장은 이 앱이 근거를 갖고
  있지 않습니다. 임상시험을 거치지 않은 소프트웨어가 할 수 있는 말이 아닙니다.
- **법적으로 그 주장을 하는 순간 의료기기가 됩니다.** 질병의 진단·예방·치료를 목적으로
  표방하면 의료기기 규제 대상이 되고, 허가 없이 그렇게 광고하는 것은 위법입니다.
  웰니스 제품과 디지털 치료기기(DTx)를 가르는 선이 바로 이 표방 여부입니다.
- **낙인 문제도 있습니다.** "치매"라는 단어가 화면 전면에 있으면 앱을 켜는 것 자체가
  자기 상태를 인정하는 행위가 됩니다. 가족이 권하기도 어려워집니다.

이 원칙은 카피에만 적용되는 게 아니라 **기능 설계에 그대로 박혀 있습니다.** 등급·신호등·
백분위를 만들지 않고, 또래 비교를 하지 않고, 표본이 적으면 점수를 만들지 않고, 쉬었다고
점수를 깎지 않는 것 전부가 같은 결정의 다른 얼굴입니다. 웰니스 고지
(`components/WellnessNotice.jsx`)는 문구를 한 곳에서만 정의해 모든 화면 하단과 설정에
노출합니다.

## 데이터 모델

모든 접근은 `src/lib/storage.js` 한 곳을 통합니다(`localStorage` 키: `cognitive-care.appState.v1`).
JSON이 깨지거나 저장이 실패해도 예외를 던지지 않고 조용히 초기 상태로 복구합니다.

```
UserProfile      { name, ageBand, largeText, voice, createdAt }
Session          { id, date, gameId, courseId, domain, level, score, accuracy, durationSec }
                   - gameId:   'shopping' | 'cooking' (이후 'wayfinding' | 'medication' 추가 예정)
                   - domain:   작업기억 · 계산 · 순서화 · 실행기능 (이후 전망기억 · 공간기억 추가 예정)
                   - courseId: 코스 플레이면 코스 id, 낱개 플레이면 null (코스 모드는 마일스톤 9)
RealWorldMission { id, date, text, done }
AppState         { schemaVersion, profile, sessions[], missions[], levels{} }
                   - levels: { [gameId]: number }  게임별 현재 난이도(1~5), lib/adaptive.js 가 조정
```

`schemaVersion`이 다르거나 저장된 것이 없으면 지난 2주치 데모 시드(`lib/seed.js`)를 채워, 가족
화면과 기능 프로파일이 처음부터 의미 있게 보이도록 합니다. 설정 화면에서 언제든 데이터를 완전히
초기화할 수 있습니다(되돌리기 전 확인 단계 포함).

## PWA (홈화면 추가 · 오프라인)

`vite-plugin-pwa`로 manifest와 서비스 워커를 만듭니다(`vite.config.js`).

- **홈화면 추가:** `display: standalone`, `orientation: portrait`. 가로로 눕히면 큰 글자가
  한 줄에 들어가지 않아 세로로 고정했습니다. 아이콘은 192·512 + maskable 512(`public/`).
- **오프라인:** 앱 껍데기와 정적 자원을 미리 캐시하고, `navigateFallback`으로 `/family` 같은
  주소에 오프라인으로 바로 들어와도 SPA 라우터가 받도록 했습니다. 훈련 데이터는 원래
  `localStorage`에만 있으므로 네트워크 없이도 그대로 읽고 씁니다 — **모든 기능이 오프라인에서
  동작합니다.**
- **업데이트:** `registerType: 'autoUpdate'` + `skipWaiting`. "새 버전이 있습니다. 새로고침
  하시겠습니까?" 같은 팝업을 띄우지 않습니다. 고령자에게 판단을 떠넘기는 물음이고, 한 화면에
  한 가지 행동이라는 원칙(`SPEC.md` 3장)에도 어긋나기 때문입니다.
- **개발 중에는 꺼져 있습니다** (`devOptions.enabled: false`). 서비스 워커가 옛 파일을 물고
  있으면 코드를 고쳐도 화면이 그대로여서 원인을 찾기 어렵습니다. `SPEC.md`가 PWA를 마지막
  마일스톤으로 미룬 이유이기도 합니다.

확인 방법:

```bash
npm run build && npm run preview
# http://localhost:4173 접속 → 주소창의 설치 아이콘으로 홈화면 추가
# 서버를 끄고 새로고침해도 앱이 그대로 뜨면 오프라인 동작 정상
```

## 디자인 시스템

토큰과 규칙은 전부 [`tailwind.config.js`](./tailwind.config.js) 한 곳에 정의하고 이유까지 적어
두었습니다. 화면 코드에는 임의 값(`text-[1.35em]` 같은 것)을 두지 않습니다.

| | 규칙 |
|---|---|
| **글자** | body 20 · button 24 · lead 28 · title 32 · hero 44 (px, 전부 rem 기반) |
| **테두리** | 누를 수 없는 면 `border-2` · 누를 수 있는 것 `border-4` |
| **간격** | 촘촘한 수치 목록 2 · 항목 목록 4 · 카드 사이 5 · 카드 안 큰 구분 6 |
| **카드** | `rounded-card` + `border-2 border-line` + `p-6` + `shadow-card` (`components/Card.jsx`) |
| **카드 안 하위 면** | `rounded-card` + `border-2` + `px-4 py-4` |
| **버튼** | `components/BigButton.jsx` 의 primary / secondary / danger 세 가지만 |
| **파랑 단계** | 50 정보 면 · 100 고른 상태 · 200 정보 면 테두리 · 300 보조 버튼 · 500 포커스 · 600 주 버튼 · 700 강조 수치 · 800 제목 |

"글자 크게"를 켜면 `<html class="large-text">` 하나로 위 수치가 전부 정확히 1.25배가 됩니다.
크기를 px 로 박아 둔 곳이 생기면 이 토글이 그 부분만 건너뛰게 되므로, 새 값을 넣을 때는
반드시 rem 기반 토큰을 씁니다. (Recharts 처럼 숫자만 받는 곳은 `largeText` 를 직접 읽어
같은 배수를 곱해 줍니다 — `components/ProfileChart.jsx` 참고)

| 미션·훈련 완료 | 체크 표시가 살짝 커지며 나타남 | 240ms |

그래서 **없는 것들:** 폭죽·색종이·반짝임, 콤보·연속 정답 강조·랭킹, 타이머 압박 연출,
화면 흔들림, 캐릭터·마스코트, 오답 시 부정 연출. 아무것도 알려 주지 않고 자극만 주는
연출이라 넣지 않았습니다(`SPEC.md` 12장).

지키는 것:

- 전부 0.5초 이내, ease 계열. 튕기거나 흔들리지 않습니다.
- `prefers-reduced-motion` 을 존중합니다. 운영체제에서 "동작 줄이기"를 켜면 CSS 쪽은
  `src/index.css` 의 일괄 규칙이 끄고, 장바구니 이동 효과는 JS 에서 아예 만들지 않습니다.
- **움직임이 정보 전달의 유일한 수단이 되지 않습니다.** 애니메이션이 끝난 뒤의 정지 화면만
  봐도 상태를 알 수 있습니다(담긴 개수·순서 번호·체크 글자).

## 접근성 원칙 (요약)

고령자 접근성이 이 앱의 최우선 설계 원칙입니다. 전체 내용은 [`SPEC.md` 3장](./SPEC.md#3-고령자-접근성-최우선-원칙--모든-화면에-적용) 참고.

- 본문 최소 20px · 버튼 24px · 제목 32px, 설정에서 "글자 크게"(1.25배) 토글 제공.
- 모든 버튼·선택지 최소 터치 영역 64px.
- WCAG AAA 지향 대비, 회색 위 회색 텍스트 금지.
- 하단 큰 탭 3개만, 깊은 메뉴 계층 없음. 한 화면에 한 가지 주요 행동.
- **드래그 앤 드롭 금지** — 순서를 정하는 과제는 전부 탭으로만 가능합니다.
- 클릭 가능한 요소는 반드시 `<button>`, hover에만 의존하는 정보 없음.
- 정답/오답은 색+아이콘(+음성 옵션 시 소리)으로 즉시, 실수해도 벌점 없이 격려 위주 카피.

### 포커스 표시를 주황에서 파랑으로 바꾼 이유

원래 키보드 포커스 링은 포인트 컬러인 주황(`accent-500`)이었습니다. 어두운 네이비 버튼 위에서도
잘 보였기 때문인데, 이 앱에서 주황·빨강 계열은 **오답**과 **되돌릴 수 없는 행동**(데이터 초기화)
에만 쓰입니다. 그래서 Tab으로 옮겨 다니기만 해도 가는 곳마다 경고가 켜지는 것처럼 읽힙니다.
실수해도 벌점을 주지 않는다는 원칙과 어긋나서, 중립적인 파랑(`primary-500`)으로 바꿨습니다.

색만 바꾸면 같은 계열인 네이비 버튼 위에서 링이 묻히므로, 요소와 링 사이 3px 틈을 흰 테두리로
채웠습니다(`box-shadow`). 밝은 배경에서는 배경과 같아 보이지 않고, 어두운 버튼 위에서는 흰 띠가
생겨 링이 항상 떠 보입니다. 어떤 배경에서도 흰색 대비 6.4:1이 유지됩니다.

## 이후 확장 아이디어

지금은 로컬 프로토타입이지만, 다음 방향으로 확장할 수 있도록 구조를 잡아 두었습니다.

- **백엔드 전환:** `src/lib/storage.js`가 유일한 저장소 접근 지점이므로, 이 파일의 구현만
  API 클라이언트로 교체하면 나머지 코드(스토어·화면·게임 로직)는 거의 그대로 유지됩니다.
- **계정·기기 간 동기화:** 지금은 "같은 기기의 `localStorage`를 가족 화면이 함께 읽는" 방식인데,
  서버가 생기면 보호자용 별도 로그인·초대 링크로 자연스럽게 확장할 수 있습니다.
- **DTx(디지털 치료기기)로의 전환:** 적응형 난이도(`lib/adaptive.js`)와 기능 프로파일
  (`lib/profile.js`)이 이미 "성적 → 난이도 조정 → 영역별 점수화" 파이프라인으로 분리돼 있어,
  임상적으로 검증된 알고리즘이나 규제 대응 로직으로 교체하기 쉬운 지점이 명확합니다. 다만 현재
  구현은 의도적으로 의료적 판정 언어를 배제했으므로, 실제 DTx 전환 시에는 웰니스 카피와
  규제 대상 카피를 분리하는 작업이 별도로 필요합니다.
- **게임 확장:** `games/gameCommon.js`(레벨 clamp·세션 레코드 생성)와 `lib/games.js`(메타데이터
  레지스트리) 덕분에 새 게임을 추가해도 홈 추천·훈련 목록·기능 프로파일 축이 자동으로 따라옵니다.
- **코스 모드:** 여러 게임을 하나의 이야기로 묶는 기능(마일스톤 9)을 위해, 게임 로직은 이미
  서로 독립적으로 설계되어 있습니다(장보기가 실패해도 요리 게임은 정상 진행하는 식).
  `Session.courseId` 필드도 데이터 모델에 미리 뚫려 있어(지금은 항상 `null`), 코스로 플레이한
  세션과 낱개로 플레이한 세션을 나중에 구분해 집계할 수 있습니다.

### 게임 추가 — 길찾기 · 복약

`SPEC.md` 6.3·6.4에 설계만 되어 있고 구현하지 않은 두 게임입니다.

- **길찾기 (공간기억 + 순서화):** 자체 그리드/그래픽으로 동네 지도를 만들고, 정류장·가게를
  순서대로 짚어 목적지까지 가는 과제. 외부 지도 API는 쓰지 않습니다.
- **복약 시간 맞추기 (전망기억 + 실행기능):** "아침 식후 30분에 파란 약"처럼 시점과 대상을
  함께 기억했다가, 시간이 흐르는 화면에서 제때 실행하는 과제. 전망기억은 지금 두 게임이
  전혀 건드리지 못하는 영역입니다.

둘을 붙이면 기능 프로파일 축이 4개에서 6개로 늘어납니다. 차트는 **영역 목록을 고정하지 않고
실제 세션이 있는 영역만 축으로 그리므로**, `lib/games.js`에 메타데이터를 추가하고 세션에
새 `domain` 값이 들어오기 시작하면 축은 저절로 늘어납니다. 차트 코드는 손댈 필요가 없습니다.

### 이중과제(dual-task) 모드 — 앉아서 / 일어서서

인지 과제를 **가벼운 신체 활동과 동시에** 수행하게 하는 방식입니다. 걷거나 제자리걸음을 하며
장보기 목록을 외우는 식으로, 실생활에 더 가까운 조건(장을 보러 **걸어가면서** 살 것을 기억한다)
을 만듭니다.

- 화면 쪽으로는 "앉아서 / 일어서서" 모드 선택과, 신체 동작을 유도하는 안내(예: "제자리걸음을
  하면서 답해 보세요")가 추가됩니다.
- **안전이 먼저 걸리는 확장입니다.** 낙상 위험이 있는 분에게 일어선 채 화면을 보게 하는 것은
  그 자체로 위험하므로, 모드 선택 전 안전 안내와 "잡을 것이 있는 곳에서 하세요" 같은 조건,
  그리고 언제든 앉아서 모드로 되돌아갈 수 있는 경로가 반드시 함께 가야 합니다.
- 데이터 모델로는 `Session`에 `mode: 'seated' | 'standing'` 정도가 붙고, 이중과제 조건의
  성적을 단일과제 성적과 **같은 축에 섞지 않는** 처리가 필요합니다(조건이 다르면 난이도가
  다른 것이므로, 지금 레벨을 점수 천장에 반영하는 것과 같은 방식으로 다뤄야 합니다).

### 난이도의 영역별 독립 조정

지금 난이도는 **게임 단위**입니다(`AppState.levels = { shopping: 2, cooking: 3 }`). 한 게임이
영역을 둘 다루더라도 판의 난이도는 하나여서, 그 게임의 "대표 영역"(장보기=작업기억,
요리=순서화) 성적만 보고 조정합니다.

한계가 분명합니다. 장보기의 계산 단계는 레벨 4 이상에서만 나오는데, 작업기억이 약해 레벨이
올라가지 않으면 **계산은 아예 만나지 못합니다.** 반대로 계산은 쉬운데 작업기억 때문에 레벨이
낮게 유지되면 계산 과제가 계속 시시하게 느껴집니다.

영역별로 독립 조정하려면 데이터 구조를 **게임 키에서 도메인 키로** 바꿔야 합니다.

```
현재: levels { shopping: 2, cooking: 3 }
전환: levels { 작업기억: 2, 계산: 4, 순서화: 3, 실행기능: 2 }
```

- `lib/adaptive.js`의 `nextLevelForGame(...)`이 `nextLevelForDomain(...)`이 되고, 대표 영역만
  보던 필터가 없어집니다(이미 세션은 영역별로 나뉘어 저장되므로 입력 데이터는 그대로 씁니다).
- 게임 화면은 "이 판의 레벨" 하나가 아니라 **단계별로 다른 레벨**을 받게 됩니다. 장보기라면
  목록 길이는 작업기억 레벨로, 계산 문항의 단위는 계산 레벨로 정하는 식입니다.
- `storage.js`에 `schemaVersion` 마이그레이션이 필요합니다. 기존 `{ shopping: 2 }`를 그 게임의
  영역들에 펼쳐 넣는(`{ 작업기억: 2, 계산: 2 }`) 변환 한 번이면 됩니다.
- 부수 효과로 **레벨 4 이상에서만 등장하는 보조 과제의 노출 문제가 풀립니다.** 계산 레벨이
  독립적으로 오르면 작업기억 레벨과 무관하게 계산 단계를 만날 수 있습니다.
